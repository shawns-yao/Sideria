# 任务执行、恢复与审计

更新日期：2026-10-06  
状态：设计阶段，尚未实现和验证

## 任务模型与故障恢复

中心保存任务期望和调度记录，Agent 保存执行事实和本地日志。关闭浏览器不应取消已提交的后台任务；模型不可用也不应使已下发的确定性操作丢失执行状态。

## Task、Step、目标执行与 Attempt

Task 表达一个用户目标，Step 表达一项操作或依赖阶段；每个 Step 在一个或多个明确目标上产生目标执行记录，每次尝试保存独立 Attempt。单机操作也使用同一模型，不另建一套批量任务系统。

例如“更新 A、B、C 三台机器上的 Nginx 配置，然后重启”可以表示为一个 Task：更新配置 Step → 验证配置 Step → 重启服务 Step，每个 Step 下分别记录 A、B、C 的执行结果。

步骤依赖需明确是各主机独立推进，还是所有目标成功后才进入下一步。遇到单机失败时继续、暂停还是终止，也由任务模板和已批准方案规定，不能由 AI 在执行途中隐式决定。每个目标只能在其所需前置步骤满足后执行后续操作。

## 状态与故障恢复

任务至少包含：任务 ID、用户目标、入口来源、目标范围、步骤依赖、操作类型、参数摘要、创建者、创建时间、截止时间、审批与授权引用、执行次数、阶段、退出结果和日志引用。秘密参数单独传递并脱敏，不直接写入审计和普通任务记录。

建议状态：待执行、执行中、成功、失败、已取消、状态待确认。取消请求与已确认取消分开处理；取消不表示已撤销外部副作用。

- Agent 对重复目标执行 ID 和 Attempt ID 返回已有状态，防止重连重复启动同一次尝试；不以顶层 Task ID 阻止其他步骤执行。
- 连接断开时标记状态待确认，重连后查询本地执行记录。
- 重试产生独立尝试记录，不覆盖首次失败。
- 不因网络超时自动重复安装、删除、重启或部署操作。
- 同一服务器的冲突任务串行，例如同时修改同一代理配置或 Compose 项目。
- 中心重启后恢复待确认任务；目标系统实际状态仍需复核。
- 无法保证任意外部操作严格只执行一次，不能将任务 ID 去重描述为完整事务保证。

超时首先表示在期限内未取得确认结果，不直接证明目标操作没有发生。Agent 执行一半掉线或中心重启时，先查询已保存的执行事实和目标状态，再决定下一步。无法确认时保留“状态待确认”，不自动当成失败重新执行。

重试由 Action 与具体操作影响决定。读取可以在声明条件下有限重试；重启会影响业务，删除可能不可恢复，均不能套用统一的网络重试策略。重试需要新的 Attempt，并重新检查当前状态、授权有效性及必要审批。

Task 和 Step 的汇总状态需保留部分成功、部分失败和未确认目标，不能用单个成功标志掩盖批量任务中的失败。具体汇总规则、并发上限、记录保留期和故障恢复流程需要在任务调度实现前确认。

## 操作历史与审计

审计应能回答：谁、何时、在哪个目标、因为什么目标或请求、通过哪个入口、执行什么 Action、依据什么授权、修改前后是什么状态、最终结果是什么。

记录串联 Task、Step、目标执行、Attempt、审批、日志和必要快照引用。AI 生成的理由标记为方案说明，不当成已证实的故障原因。状态时间线用于排查和复盘，审计记录本身不保证任意操作可以回滚。

修改前后状态只记录必要、受权限约束的信息；大文件和秘密使用摘要或受保护引用，不将完整敏感内容复制进普通审计。

## 查询、分析与任务的关联

完整任务模型用于需要持久进度和恢复的后台操作。普通查询、持续指标和交互会话的生命周期见[通信设计](communication.md)，不统一包装为多步骤 Task。

AI 的一次分析保存用户目标、目标范围、工具调用引用和建议版本，使用 Analysis ID 关联轻量查询。建议转为执行时生成新的 Task，并引用分析证据和方案版本；“已生成建议”不是“任务执行成功”。

工具共享确定性执行结果。模型不可用时保留已有分析和执行事实，已授权下发的后台任务按原策略继续，不依赖模型补出结果。


## 幂等与限流

API 受理、任务投递、Agent 执行三层去重和 Redis 租约规则见[可靠性设计](reliability.md)。重复消息与主动重试分开处理；数据库持久投递状态配合 Agent 本地事实恢复，不能只靠 Redis 锁。
