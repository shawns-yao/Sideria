# 部署、容量与技术选型

更新日期：2026-10-06  
状态：设计阶段，尚未实现和验证

## 部署位置与资源影响

中心建议放在稳定、持续在线的机器上，优先位于实验 Kubernetes 集群之外。中心不可用时，既有业务继续运行，但集中查询、调度和告警可能中断。

前端构建产物使用 Go embed 嵌入中心程序。生产环境无需运行 Node.js；发布对应系统和架构的中心及 Agent 二进制。Docker 镜像作为可选交付方式。

PostgreSQL 作为中心的独立数据库服务部署，可以与中心同机或部署在独立机器上；中心二进制不包含数据库服务。数据库连接仅向中心开放，受管服务器无需安装 PostgreSQL。

基础指标采集、目录浏览、大文件传输、递归扫描、镜像构建和软件安装的开销不同。通过采样周期、缓存上限、并发限制、流式传输和日志保留控制资源使用。

尚无 Agent CPU、内存、带宽或磁盘占用的实测结果，不承诺固定资源数字。特别区分面板 Agent 的开销与 Kubernetes 本身的开销。

多地区服务器可以集中管理，但不因此应组成同一个集群。集群选机需考虑节点间连通性、时延、SSD、架构兼容、剩余资源和业务可用性要求。

## 技术选型

| 组件 | 已定方向 | 边界 |
| --- | --- | --- |
| 中心与主机 Agent | Go | 模块化单体中心；每主机一个受控执行器 |
| Redis | 中心依赖 | 限流、短期缓存与租约，不作为任务唯一存储 |
| 前端 | Vue 3 + TypeScript | 构建后嵌入中心 |
| 结构化数据 | PostgreSQL | 独立服务，不下发数据库凭据给 Agent |
| 网页终端 | xterm.js | 连接中心转发的 PTY 数据 |
| 指标采集 | gopsutil 与必要的系统专项采集 | 需要验证统计口径及目标系统支持 |
| AI 模型 | 中心接入，提供方与模型待确认 | 受管主机不运行 LLM；模型 API Key 仅中心使用 |

## Redis 部署

Redis 可与中心同机或独立部署，只允许中心访问，凭据不下发到 Agent。容量、淘汰、持久化与故障策略须按数据用途确定，见[可靠性设计](reliability.md)。引入 Redis 增加中心依赖与运维成本，不增加每台受管服务器的安装要求。

## AI 成本与可用性

MVP 即需要模型接入配置和失败处理。限制每次分析的工具次数、日志字节、持续时间及模型上下文预算；达到上限时返回已有证据和未完成项，不无限循环。

模型不可用时界面明确告知分析失败，基础监控、文件和已授权的确定性操作仍可使用；降级不代表 AI 功能通过验收。

模型请求延迟和费用、中心负载、Agent 开销分别测量。模型提供方式、数据外发范围与保留策略在实际调用前确认。

## 环境待确认

用户已提供首批规格：4 核 / 8 GB / 带宽标记 2M，2 核 / 4 GB / 带宽标记 30M；机器分布于不同厂商和地区，包含空闲与正在承载业务的服务器。带宽标记的单位、方向、突发和流量限制尚未核实，不能据此直接计算上传预算或确定中心位置。首版必须支持逐主机配置采样、传输限制，不能把繁忙机器当成空闲测试机。

AI 接口方向已确认为中心调用 OpenAI 兼容 Responses API，具体提供方、模型和外发范围在实际接入前确认。前端独立开发不依赖这些凭据。

- 首批服务器的 Linux 发行版、版本和 CPU 架构。
- 服务器数量、地区、中心放置位置及实际网络可达性。
- Agent 执行身份、需要开放的操作和提权范围。
- Docker/Compose 版本与首批安装模板。
- Kubernetes 发行版、已有集群情况与连接器权限范围。
- PostgreSQL 版本、部署位置、连接方式和备份恢复要求。
- Redis 版本、部署位置、容量、数据隔离、过期和故障策略。
- AI 模型提供方式、数据外发范围和秘密管理方式；MVP 接入 AI 前确认。
- 指标保留、日志容量和通知渠道。

以上缺项在对应阶段确认，不阻塞独立模块的设计，但不能凭名称猜测目标机器能力。
